# PlcBridge 产品方案（精简版MVP）

> **交付范围**：4个月核心交付
>
> 本文定义PlcBridge的MVP（最小可交付产品）。特性按优先级分批交付，不一次性做完整企业版。

## 1 项目概述

### 1.1 产品定位

基于Go+Vue3+ElementPlus开发的工业PLC采集与指令回写平台。**采集 / 转发 / 回写一体化部署在同一进程内**（通过独立 goroutine 池物理隔离，§6.2.2），支持S7、ModbusTCP、OPCUA多协议采集与回写。
解决原有平台"回写卡死采集"的架构问题（之前因 Node.js 单线程 + 开发不当导致），提供稳定可靠的数据采集与指令回写能力。

### 1.2 MVP核心功能

1. **单进程多 worker 池隔离**：采集/转发/回写在**单一进程**内通过独立 goroutine 池物理隔离（collectPool / forwardPool / writePool），详见 §6.2.2「进程内隔离」。
2. **多协议采集**：支持S7、ModbusTCP、OPCUA三种主流工业协议
3. **数据转发**：内置MQTT、InfluxDB两种转发Target
4. **指令回写**：外部系统通过RESTful API下发回写指令到PLC
5. **配置同步**：基于跨平台文件监听的配置热更新机制（Linux inotify / Windows ReadDirectoryChangesW）
6. **基础监控**：Prometheus指标 + 健康检查

### 1.3 MVP不做

详细不做清单见[附录A.2](#a2-mvp不做明确排除)。

## 2 性能指标

> **修订说明（2026-09-25 重构）**：以"**Go + 单进程（采集/转发/回写多 worker 池隔离）+ 工业协议 + 普通硬件，可实现行业基准普通水平**"为核心概念重写全部性能指标。所有数字的来源类型收窄为 4 类：`[行业基准]`、`[协议物理层]`、`[工程估算]`、`[TBD-未确认]`。**没有外部依据的来源类型已删除**。

> **§2 性能指标的核心约束**：Go + **单进程**（采集 / 转发 / 回写通过 worker 池物理隔离）+ 工业协议（S7/ModbusTCP/OPCUA）+ 普通硬件（2~8 核 / 4~16GB 工业 PC / 边缘网关），**可实现 IndustryBenchmark.md 定义的「普通水平」**——即 §2.1 三档均落在普通水平区间内，不向行业金标准（Kepware/Ignition）看齐。区间取值规则：
>
> - 数字取 **IndustryBenchmark 普通水平区间的中间值**（避免取上限被现实打脸，避免取下限显得保守）
> - 来源优先 **[行业基准]**（IndustryBenchmark.md §1）；协议本身限制用 **[协议物理层]**（S7 PDU 32 元素、Modbus 125 寄存器等）；10 万点位内存/CPU 这类纯数学推导用 **[工程估算]**
> - 用户场景、单点需求这类**实际部署条件未知**的内容标注 **[TBD-未确认]**，等待用户输入

> **§2 与单进程架构的协同**：所有 §2 性能指标在**单进程内**通过 4 条工程硬约束实现（详见 §6.2.2「进程内隔离」）。**单进程不意味着无隔离**——隔离发生在 worker pool / connection pool / channel 三层：
> 1. **worker 池物理隔离**：`collectPool` / `forwardPool` / `writePool` 三个独立 goroutine 池，代码 review 拒掉跨池混用
> 2. **连接池物理隔离**：PLC 读连接池 / 写连接池 在进程内独立配置，互不影响 PLC 端并发墙
> 3. **有界队列 + 超时**：回写有界队列（1024），满了直接拒；所有 IO 操作 300ms 超时
> 4. **关键路径 P99 监控**：采集 P99 / 回写队列长度 / 各 worker 池利用率 独立打点

> **历史背景**：2026-09-25 之前是「采集+转发服务 A / 回写服务 B」双进程架构；之前曾因 Node.js 单线程 + 开发人员限速不当导致「回写卡死采集」。改用 Go + 单进程多 worker 池后，goroutine 独立调度 + 上述 4 条硬约束 = 工程上等价于双进程隔离，但部署复杂度大幅降低。

### 2.2 性能指标的推导链

每个数字对照 IndustryBenchmark.md §1 与 IndustryBenchmark.md §2 的协议物理层事实，让指标**站得住脚**而非凭感觉给出。推导原则：**优先引用 IndustryBenchmark；其次引用协议本身硬约束（S7/Modbus/OPC UA）；最后才用工程估算（数学对但前提标注清楚）**。

#### 2.2.1 单 PLC 采集耗时 ≤ 300ms（推荐基线）的推导

```
[协议物理层] IndustryBenchmark §2.3 协议 RTT：
  Modbus TCP 单次读 5~50ms（含网络）；S7 单次读 30~150ms；OPC UA 50~300ms
[协议物理层] 批量读 200 点场景：S7 7 包串行 ≈ 560ms；Modbus 2 包 ≈ 100ms；OPC UA ≈ 200~600ms
[协议物理层] IndustryBenchmark §2.3：S7-1500 单 PLC 并发上限 8~16
[行业基准] IndustryBenchmark §1 单 PLC 采集 P99 普通水平区间 200~500ms（取中间偏下 300ms）
推导：单 PLC 一个采集周期 P99 占用 IndustryBenchmark 普通水平区间内部分位置；
     基线档 200 PLC × 1s 周期下，并发不会撞 PLC 端并发墙
结论：P99 ≤ 300ms 是可达的（位于 IndustryBenchmark 普通水平中位）
```



#### 2.2.2 普通回写 P99 ≤ 500ms 的推导

```
[行业基准] IndustryBenchmark §1 回写 P99 普通水平区间 300~800ms（取中位偏下 500ms）
[行业基准] IndustryBenchmark §2.4 链路段典型耗时合计：300~800ms（普通水平合计）
推导：500ms 落在 IndustryBenchmark 普通水平中位（300~800ms）
     网络抖动在最坏 1% 场景下仍 ≤ 800ms（普通水平上限；MVP 不重试，超时即 503）
结论：P99 ≤ 500ms 是可达的（位于 IndustryBenchmark 普通水平中位偏下）
```



#### 2.2.3 配置生效 ≤ 2s（推荐基线）的推导

```
[行业基准] IndustryBenchmark §1 配置生效普通水平区间 1~5s（取中间偏下 2s）
[协议物理层] 文件监听（inotify / ReadDirectoryChangesW）触发延迟 50~500ms
[协议物理层] 内存原子替换（atomic.Pointer[Config]）延迟 < 10ms
推导：监听触发 100ms → 去抖 1s → 内存热替换 100ms → 服务间同步 100ms
     总计 1.3s ≈ 2s（IndustryBenchmark 普通水平区间内）
结论：配置生效 P99 ≤ 2s 是可达的
```



#### 2.2.4 单实例 PLC 上限的推导

```
[协议物理层] PLC 端并发硬约束：S7-1500 8~16 / S7-1200 4~6 / S7-200 SMART 1~2 / 三菱 FX5U 2~4
[行业基准] IndustryBenchmark §1 单实例 PLC 普通水平 100~300；IndustryBenchmark §2.1 论证 300 是普通上限
推导：单 plcbridge 实例 300 连接 / PLC 协议并发系数 = 单实例合理上限
     IndustryBenchmark §1 单实例 PLC 普通水平上限 300
     超过此规模走水平扩展（多 plcbridge 实例）
结论：§2.1.2 高密度档 300 PLC 是 IndustryBenchmark 普通水平上限
```



### 2.3 端到端延迟组成

> **本节依据 IndustryBenchmark.md §2.4「回写链路典型耗时」。IndustryBenchmark.md 已给出各段典型耗时区间，本节只做 PlcBridge 视角的链路映射，不重复 IndustryBenchmark 已有的数据。** 各链路环节典型耗时、依据 IndustryBenchmark.md §2.4 的对应表格：

> **单进程架构的关键差异**：原「服务 B → 服务 A（gRPC/HTTP 5~20ms）」现在降为**进程内 channel 通信（< 1ms）**——回写延迟比双进程少一跳（少 5~20ms）。本表保留 IndustryBenchmark 通用数据，但在「PlcBridge 对应实现」列标注本架构的实际链路形态。

| 链路环节                   | 典型耗时（IndustryBenchmark §2.4）          | PlcBridge 对应实现（单进程）                              |
| ---------------------- | ------------------------------------- | ------------------------------------------------- |
| Web → plcbridge（HTTP 路由）| 5~20ms（普通水平）                          | Go net/http + Bearer Token                        |
| plcbridge 鉴权 + 点位表查询   | （IndustryBenchmark 未单独列，按内存读 ≈ 1~3ms） | Go 内存 map 命中索引                                    |
| plcbridge → PLC 写入      | 50~500ms（取决于 Target 类型，普通水平）          | MQTT 5~10ms / Kafka 10~20ms / InfluxDB 20~50ms |
| PLC → 确认响应             | 50~200ms（普通水平）                        | 由 PLC 协议决定                                        |
| **普通水平合计**             | **300~800ms**（IndustryBenchmark §2.4） | **§2.1.2 基线档 P99 ≤ 500ms** 落在该区间中位               |
| **优秀水平合计**             | 100~300ms（IndustryBenchmark §2.4）     | 不在本表覆盖范围（三档未承诺优秀水平）                              |

> **单进程相比双服务的延迟优势**：原双服务架构下回写链路的「进程间 RPC（5~20ms）」在单进程内降为 channel 通信（< 1ms），回写 P99 总计节省约 5~20ms。该优势在 §2.1.2 基线档 P99 ≤ 500ms 内已计入，不重复承诺。




### 2.4 关键约束（物理层硬上限）

1. **PLC 端并发上限**：[协议物理层] S7-200 SMART 1~~2、S7-1200 4~~6、S7-1500 8~~16、三菱 FX5U 2~~4、施耐德 M340 6~8。超出排队，**单实例 goroutine 数量无意义**。
2. **单 PLC 采集周期下限（基于 S7 批量读）**：[协议物理层] S7 单包 32 元素/PDU，200 点单 PLC 串行批量读 ≈ 560ms；含网络抖动建议 **1Hz（1000ms）**为安全值。**100ms 周期必须配合 §6.1 采样策略，不能所有点位都 100ms 采**。
3. **S7 单 PLC 采集物理下限在 500~600ms**：[协议物理层] S7 协议 PDU 32 元素上限决定单 PLC 串行批量读 200 点 ≈ 560ms；§2.1.2 高密度档已说明 **P50 ≤ 300ms / P99 ≤ 500ms**（P99 含网络抖动上限到 IndustryBenchmark 普通水平 500ms），**不向优秀水平 <200ms 看齐**。
4. **Modbus 串行约束**：[协议物理层] 同一从站必须串行访问，单连接复用；批量读按 Modbus 协议单包 125 寄存器上限打包。
5. **单实例点位上限受 PLC 端硬约束，不是 Go 性能限制**：[协议物理层] 超出 IndustryBenchmark §1 普通水平上限 10 万点位时优先水平扩展而非单实例堆叠（§2.2.4 推导）。
6. **网络抖动不可避免**：[协议物理层] 跨网段 / 跨机房的 RTT P99 可达 50~100ms，§2.5 监控指标必须能在 P99 突变时触发告警。



### 2.5 监控指标（性能基线对照）

每行指标的报警阈值 = §2.1.2 对应档位 P99 数字（不加缓冲余量，让告警真实反映性能漂移）。阈值依据：

- 单 PLC 采集耗时、回写、配置生效：**§2.1.2 对应档位 P99**
- 队列长度 / 队列丢弃：**[协议物理层]** 有界队列（§6.1）触发丢弃的临界点
- 内存 / goroutine：**[协议物理层]** Go runtime / 容器限额


| 指标             | 推荐基线报警阈值    | 阈值依据                                   | 测量方法                 | 触发动作（§6 联动）  |
| -------------- | ----------- | -------------------------------------- | -------------------- | ------------ |
| 单 PLC 采集耗时 P99 | > 300ms     | **§2.1.2 基线档 P99**                     | 按 PLC 维度打点（§10.1）    | §6.2.2 熔断该 PLC（连续超时） |
| 回写 P99 延迟      | > 500ms     | **§2.1.2 基线档 P99**                     | 按 trace_id 串联（§10.2） | §6.4 告警（超时直接 503，MVP 不重试） |
| 配置生效延迟         | > 2s        | **§2.1.2 基线档 P99**                     | §6.6 时间戳差            | §6.6 告警      |
| 队列长度           | > 80% 容量    | **[协议物理层]** 有界队列触顶临界                   | §6.1 队列监控            | 队列满时丢队头      |
| 队列丢弃速率         | > 0 持续 1 分钟 | **[协议物理层]** 触顶即丢判定                     | §6.1 丢弃计数            | 触发告警         |
| 内存占用           | > 80% 限额    | **[协议物理层]** Go runtime MemStats / 容器限额 | runtime.MemStats     | 触发告警         |
| goroutine 数    | > 10 万      | **[协议物理层]** Go runtime 上限经验值           | runtime.NumGoroutine | 触发告警         |




### 2.6 降级策略

> 现场抖动时的性能降级路径——**不是故障恢复，而是性能可预期下降**。所有阈值与 §2.1.2 对应档位对齐，依据 [行业基准] 或 [协议物理层]。


| 场景              | 性能表现             | 自动行为                      | 阈值依据                                    |
| --------------- | ---------------- | ------------------------- | --------------------------------------- |
| **单 PLC 网络抖动**  | 该 PLC 采集耗时突增     | §6.2.2 熔断该 PLC（持续 10s 后恢复尝试） | [协议物理层] PLC 端超时恢复经验值                    |
| **批量 PLC 同时抖动** | 队列堆积、丢弃率上升       | §6.1 队列满丢队头（不阻塞采集）        | §2.5 队列长度阈值（80% 容量）                     |
| **Target 故障**   | 回写 P99 突增        | §6.4 告警（超时即 503，MVP 不重试，失败丢弃见 §6.4.3） | §2.1.2 基线档回写 P99 ≤ 500ms |
| **plcbridge 整体高负载** | 采集周期突破 1s、内存逼近限额 | §2.5 触发告警                 | §2.1.2 高密度档点位 / 内存 / CPU 上限             |
| **配置大文件热加载**    | 配置生效延迟 > 2s      | §6.6 跳过本次更新、保留旧配置         | §2.1.2 基线档配置生效 ≤ 2s                     |
| **plcbridge 重启**  | 期间回写请求 503       | §8.1 接口返回明确错误码            | §11.5 自动重启机制（systemd / Windows Service） |

## 4 术语表


| 术语                               | 定义                                                             |
| -------------------------------- | -------------------------------------------------------------- |
| Channel                          | 连接层抽象，按 role 区分采集侧（collect）和转发侧（forward），绑定 protocol + address |
| Source                           | 数据采集源，引用 1 个 collect Channel（1:1），包含 N 个 Point                 |
| Target                           | 转发目的地，内嵌在 Device 下，通过 source_ids + point_ids 指定转发哪些点位          |
| 点位                               | Source内的最小数据单元                                                 |
| 有界队列                             | 容量受限的内存队列                                                      |
| **collectPool**                  | **plcbridge 进程内的采集 worker goroutine 池（§6.2.2，默认 200 goroutine）**       |
| **forwardPool**                  | **plcbridge 进程内的转发 worker goroutine 池（§6.2.2，默认 100 goroutine）**       |
| **writePool**                    | **plcbridge 进程内的回写 worker goroutine 池（§6.2.2，默认 50 goroutine）**         |
| **configPool**                   | **plcbridge 进程内的配置监听 goroutine 池（§6.2.2，默认 4 goroutine）**           |
| 熔断                               | **PLC 连续超时（默认 300ms）触发，10 秒后恢复尝试（§3 关键参数）；按 PLC 维度独立，§6.2.2**         |
| 幂等                               | 同一指令多次执行结果一致                                                   |
| 文件监听                             | Linux/Windows文件变更通知（inotify/ReadDirectoryChangesW）             |
| **心跳（Heartbeat）**                | **PLC 判定"上位机存活"的探测机制。S7/ModbusTCP 需应用层实现；OPC UA/MQTT 由协议层提供**  |
| **翻转心跳**                         | **0/1 交替写一个 bool 点位，让 PLC 程序判断上位机是否在线（S7 常用方式）**               |
| **读探针**                          | **定期读一个固定寄存器，读成功 = 链路存活（ModbusTCP 推荐方式）**                      |
| **事件驱动心跳**                       | **由外部业务调用回写 API 时顺便触发心跳翻转，减少无谓 IO；需兜底定时器保证业务稀疏时心跳不中断**         |
| **兜底定时器**                        | **心跳翻转间隔上限的定时器（默认 5s），业务稀疏时自动保活**                              |
| **协议层 KeepAlive**                | **协议自带的会话保活机制（如 OPC UA Session Timeout、MQTT PINGREQ），应用层无需心跳** |
| **LWT（Last Will and Testament）** | **MQTT 客户端异常断开时由 Broker 自动推送的遗嘱消息，标准机制替代应用层翻转心跳**              |




## 5 整体架构



### 5.1 架构组成

> **单进程架构**：所有采集/转发/回写在**同一 plcbridge 二进制进程**内通过独立 goroutine 池实现，详见 §6.2.2「进程内隔离」。

| 组件          | 技术栈                     | 职责                |
| ----------- | ----------------------- | ----------------- |
| Web后台       | Go + Vue3 + ElementPlus | 配置管理、状态监控         |
| plcbridge  | Go                      | 多协议采集、转发、回写一体化（单进程多 worker 池） |

> **为什么单进程**：原计划的双服务架构（采集+转发 / 回写）在 §2 性能指标同等实现下，部署复杂度翻倍、延迟多一跳。Go 单进程 + 多 worker 池隔离的工程实践已成熟，详见 §6.2.2。




### 5.2 数据流



#### 采集数据流（plcbridge）

```
1. 按Source配置的采集周期，从PLC读取点位数据（批量读取）
2. 内存过滤（采集开关、变化阈值）
3. 匹配转发规则，写入对应Target队列
4. 异步投递下游（MQTT/InfluxDB）
```



#### 回写指令数据流（HTTP → writePool）

```
1. 外部系统下发回写指令（HTTP API，路径 POST /api/v1/write）
2. 内存缓存校验（设备总开关、Source 回写开关、点位写权限）
3. 指令进入对应 PLC 的独立 writeQueue（按 device_biz_id 分队列，容量 1024）
4. writePool 按 FIFO 顺序消费 writeQueue，执行 PLC 写入
5. 返回结果（HTTP 200 / 503 / timeout）
```

> **单进程优势**：回写指令进入 writePool **不跨进程**，延迟从原 5~20ms（HTTP/gRPC）降到 < 1ms（channel）。详见 §2.3 端到端延迟表。



#### 配置变更流程

**目标平台**：MVP支持**Linux（生产部署）+ Windows（本地开发）双平台**。

**跨平台路径**：


| 平台      | 配置目录                                                      |
| ------- | --------------------------------------------------------- |
| Linux   | `/etc/plcbridge/`                                         |
| Windows | `%PROGRAMDATA%\plcbridge\`（默认`C:\ProgramData\plcbridge\`） |
| 容器      | `/etc/plcbridge/`（默认）                                     |


**配置变更流程**：

```
1. Web后台修改配置 → 写SQLite → 导出快照（跨平台路径）
2. plcbridge 通过平台原生机制感知配置变更（Linux inotify / Windows ReadDirectoryChangesW）
3. 原子替换内存缓存，业务无中断
4. L2兜底：每60秒轮询检查配置文件mtime（跨平台通用）
```


### 5.6 紧急停机模式

**触发场景**：

- 全局配置文件设置 `emergency_stop: true`
- Web后台界面"紧急停机"按钮（最高权限）

**行为**：


| 组件          | 紧急停机时行为                          |
| ----------- | -------------------------------- |
| plcbridge   | 停止 collectPool 采集；writePool 拒绝新指令（返回 503），已入队指令清空；forwardPool 处理完积压后停止 |
| Web后台       | 显示紧急停机状态，可一键恢复                   |

> **单进程差异**：紧急停机时 collectPool / forwardPool / writePool **协调停止**——forwardPool 先处理完积压（不丢数据），再统一停止。


**恢复方式**：

- 关闭全局紧急停机标志
- plcbridge 自动恢复运行（worker 池重启，无需重启进程）
- 紧急停机期间的数据已丢弃（不补发）



## 6 核心设计规范



### 6.1 队列设计

**采集端队列（collectPool → forwardPool）**

1. **队列粒度**：每个 Target 独立队列（MQTT Topic、InfluxDB 测量隔离）
2. **队列类型**：内存有界队列
3. **入队策略**：队列满时删除队头旧数据
4. **监控指标**：队列长度、丢弃消息数（按 Target 维度）

**批量读策略（采集端点位置预处理）**

> **本节是 §2.1.2 基线档「单 PLC 采集耗时 P99 ≤ 300ms」的实现基础**。没有批量读，200 点场景下采集耗时直接撞 1 秒周期。

**为什么必须批量读**：


| 读取方式             | 200 点耗时       | 100ms 周期可行性 |
| ---------------- | ------------- | ----------- |
| 散列读（每点一次请求）      | ~1000ms（串行最坏） | ❌           |
| 整块读（一次性读全寄存器）    | ~500ms（受协议限制） | ❌           |
| **批量读（按地址合并打包）** | **80~280ms**  | ✅（1Hz 周期下）  |


**协议层批量读约束**：


| 协议        | 单包上限                  | 批量读支持           | 备注           |
| --------- | --------------------- | --------------- | ------------ |
| ModbusTCP | 125 寄存器/包             | 原生支持            | 按地址连续性打包     |
| S7        | PDU 优化（32 元素/PDU 经验值） | 无原生批量读          | 多 DBW 分散时性能差 |
| OPCUA     | 无硬限                   | Subscription 模式 | 推荐用订阅代替轮询    |


**打包策略（collectPool 启动时预处理）**：

```
启动阶段：对 Source 下所有 Point 按 [PLC地址 + 寄存器类型 + 连续性] 预分析
        生成"读包"列表：每个读包 = [起始地址, 长度, 寄存器类型]

采集时：按读包列表下发请求
       响应到达后，解析出每个 Point 的值，写入内存缓存
```

**打包合并规则**：

1. **同 Source + 同寄存器类型 + 地址连续** → 合并为一个读包
2. **同 Source + 同寄存器类型 + 地址不连续但间隔 ≤ 阈值**（默认 32 寄存器） → 合并读包 + 解析时丢弃间隙
3. **跨寄存器类型不可合并**（holding register 与 input register 协议层独立）
4. **跨 Source 不可合并**（每个 Source 独立采集，互不影响）

**降级策略**：

- 协议不支持批量读（S7 散列）→ 单点串行读，受单 PLC 300ms 超时约束
- 批量读超时 → 该读包内所有 Point 标记本周期失败，进入熔断判定
- 批量读部分成功（部分寄存器响应异常）→ 已成功的 Point 正常更新，失败的进入下一周期重试

**监控指标**：


| 指标             | 说明             | 报警阈值                |
| -------------- | -------------- | ------------------- |
| 平均读包大小         | 每 PLC 单次采集的读包数 | > 8（说明点位散列严重，需重排配置） |
| 批量读命中率         | 批量读成功 / 总采集次数  | < 95%               |
| 单 PLC 采集耗时 P99 | 端到端含批量读        | > 300ms             |


**回写端队列（writePool）**

1. **队列粒度**：每PLC一个独立队列（按device_biz_id分队列，plc_01、plc_02各自独立）
2. **队列类型**：内存有界队列，FIFO消费
3. **入队策略**：队列满时拒绝新指令并返回错误（不覆盖旧指令，避免丢指令）
4. **监控指标**：队列长度、按device_biz_id区分



### 6.2 连接管理



#### 6.2.1 协议层连接硬约束

这是**协议本身强制的限制**，无法突破：


| 协议            | 协议层硬约束                | 说明                     |
| ------------- | --------------------- | ---------------------- |
| **S7**        | **单 PLC 并发上限按型号**：S7-1500 8~16 / S7-1200 4~6 / S7-200 SMART 1~2 | 详见 §2.4 推导依据；§6.2.1 是协议层硬约束的快速索引         |
| **ModbusTCP** | 同一从机必须串行访问（1个连接）      | 协议无并发支持，同一从机多个连接无意义    |
| **OPCUA**     | 协议本身无硬限制              | 推荐Subscription模式减少连接开销 |


**Source权限的对应关系**：


| Source类型 | 协议举例                    | 连接特点        | 回写能力 |
| -------- | ----------------------- | ----------- | ---- |
| 读写设备     | S7、OPCUA、ModbusTCP（PLC） | 支持多连接（按需配置） | 是    |
| 只读设备     | ModbusTCP（传感器）、MQTT订阅   | 单连接（串行）     | 否    |
| 只写设备     | （未来扩展预留）                | 待定          | 是    |




#### 6.2.2 进程内 worker 池隔离（plcbridge 单进程架构）

> **本节是 §2 性能指标「单进程多 worker 池隔离」的实现基础**。原计划的双进程隔离（服务A / 服务B）改为单进程内的三层隔离：worker 池 / connection pool / channel。

**worker 池划分**：

| 池 | 职责 | 默认上限 | 阻塞行为 |
|---|---|---|---|
| `collectPool` | PLC 批量读、心跳读、健康探测 | 200 goroutine | 任务级非阻塞（借出超时 100ms）|
| `forwardPool` | Target 投递（MQTT/InfluxDB/Kafka）| 100 goroutine | 任务级非阻塞 |
| `writePool` | 回写指令消费、PLC 写入 | 50 goroutine | 任务级非阻塞 |
| `configPool` | 配置监听、热加载 | 4 goroutine | 阻塞可接受 |

> **worker 池硬隔离规则**：
> 1. collectPool / forwardPool / writePool 三个池**代码 review 拒掉跨池混用**——例如不能在 collectPool 里直接执行回写
> 2. 每个池独立 `context.Context`，互不传染超时
> 3. 池间通信**只通过 channel**，不共享可变状态

**连接池隔离**：

- `readConnPool`（plcbridge 进程内）：PLC **读**连接池，独立配置
- `writeConnPool`（plcbridge 进程内）：PLC **写**连接池，独立配置
- 读写连接池**完全隔离**——回写挤爆写池不会影响采集连接

**熔断机制**：

- **单PLC独立超时（默认300ms）**，超时触发熔断该 PLC（不影响其他 PLC）
- 熔断后等待 10 秒重试（与 1Hz 采集周期匹配；§3 关键参数）
- 熔断状态按 PLC 维度记录，**只影响 collectPool 与该 PLC 相关的任务**——writePool 对同一 PLC 的回写不受影响（独立的写连接 / 独立 worker）



#### 6.2.3 现场连接预算分配（工业实践）

**为什么必须预估**：

- 工厂现场PLC往往被多个系统同时访问
- 常见搭配：WinCC/SCADA（HMI监控)+ MES（生产执行）+ PlcBridge
- 如果PlcBridge占用全部连接，其他系统会断连

**连接预算分配示例**：

```
场景：1台S7-1500 PLC

S7-1500 PLC协议上限 ≈ 16 个并发连接（§2.4 推导依据）
├─ WinCC占用 = 2（HMI监控，稳定）
├─ MES占用 = 4（生产执行，稳定）
└─ PlcBridge可用 = 8（推荐上限，占用 总数1/2）

PlcBridge内部设计（示例，按统一 Channel 模型，§4 术语表）：
└── 设备 plc_01
    ├── Source s7_main（采集源）
    │   └─ 引用 collect Channel ch_s7_plc_01（连接数=1，给 readConnPool）
    └── Target t_mqtt_plc_01（转发目标）
        └─ 引用 forward Channel ch_mqtt_main（连接复用，与采集无关）

回写 PLC 写入：走 writePool 的写连接池，与 readConnPool 独立，但**复用同一 Channel ch_s7_plc_01**——按 §6.2.2 隔离规则。
总计 1 个 S7 连接 + 1 个 MQTT 连接（<< 8 S7 上限，保守且合理）。
```

> **重要**：本例中 S7-1500 上限是 16，不是文档早期版本中的「64」——后者是 S7-300/400 时代的旧数字。S7-1500/1200/200 SMART 上限按 §2.4 推导依据表（S7-1500 8~16 / S7-1200 4~6 / S7-200 SMART 1~2）。

**设计原则**：

- PlcBridge占用 = 该PLC总连接数的**1/4~1/2**（不同 PLC 型号上限差异大，按 §2.4 表分型号）
- ModbusTCP传感器类：每台设1个连接（协议约束，无需配置）
- 采集/回写共享同一个 collect Channel，由 collectPool（读连接池）和 writePool（写连接池）分别消费——**不需要为写单独建 Source**
- **单 Source 连接数 = 1**（除非有特殊性能需求再调整，如高频回写可上调到 2~4，§6.2.3 末表）



#### 6.2.4 PLC 连接池机制

> **本节是 §2 推荐基线"200~300 PLC / 单实例"的实现基础**。没有连接池，每个 PLC 一根连接既慢又耗资源。

**与 §6.2.2 的关系**：6.2.2 是"连接池设计原则"（隔离 + 熔断），本节是连接池的**具体实现机制**（建连 / 复用 / 健康检查 / 释放）。

##### 池的划分


| 池              | 归属进程 | 归属 worker 池    | 用途              | 池上限              |
| -------------- | ---- | -------------- | --------------- | ---------------- |
| PLC 读连接池       | plcbridge | collectPool   | 采集读 + 心跳读 + 健康探测 | **300 连接**（推荐基线） |
| PLC 写连接池       | plcbridge | writePool     | 普通回写           | **300 连接**       |
| Target 下游连接池   | plcbridge | forwardPool   | 转发到 MQTT/Kafka/DB | 按 Target 维度配置    |

> **单进程下的池归属**：三个连接池都在 plcbridge 进程内，但通过 worker 池（collectPool/writePool/forwardPool）物理隔离——读连接只被 collectPool 借用，写连接只被 writePool 借用，代码层不可越界。




##### 连接生命周期

```
[新建] ─握手成功─> [空闲] ─被借出─> [使用中] ─归还─> [空闲]
                      │                                       │
                      ├─健康检查失败─┐                          │
                      │              ↓                          │
                      │         [隔离] ─健康检查通过─> [空闲]    │
                      │              │                          │
                      │              └─连续 N 次失败─> [销毁]   │
                      │                                        │
                      └─空闲超时(默认 5 分钟)─────────────────> [销毁]
```



##### 关键参数


| 参数       | 默认值                 | 说明                                   |
| -------- | ------------------- | ------------------------------------ |
| 池初始连接数   | `min(配置值, PLC 实际数)` | 启动时不全量建连，按需增长                        |
| 池最大连接数   | **300**（推荐基线）       | 超出拒绝新建，复用已有                          |
| 单连接空闲超时  | 5 分钟                | 超时归还 → 销毁                            |
| 单连接最大寿命  | 1 小时                | 防 TCP 半开/僵尸连接                        |
| 健康检查间隔   | 30 秒                | 空闲连接定期 ping                          |
| 健康检查失败阈值 | 3 次连续失败             | 进入"隔离"状态                             |
| 隔离期      | 10 秒                | 隔离期内不参与复用                            |
| 借出超时     | 100ms               | goroutine 等待连接的最长容忍；超时则采集该 PLC 本周期失败 |
| 握手超时     | 2 秒                 | 建连握手的最长等待                            |




##### 借出策略（最关键）

plcbridge 收到 PLC `plc_01` 的采集请求时：

1. **查池**：找 `plc_01` 对应的连接
2. **空闲连接**：直接取出使用
3. **无空闲连接**：
  - 当前总连接数 < 池上限 → **新建一个**（握手 100~300ms 阻塞当前 goroutine）
  - 当前总连接数 ≥ 池上限 → **借出超时（100ms）**，超时则该 PLC 本周期采集失败
4. **单 PLC 维度串行**：同一 PLC 的多个采集 goroutine 在池入口排队，保证**同一 PLC 内采集串行**（避免撞 PLC 端并发墙）

> **关键设计**：连接池是**按 PLC 维度**隔离的，不是全局共享。每个 PLC 在池内有自己的连接列表，互不影响。



##### 单 PLC 连接数配置


| 场景               | 单 PLC 连接数 | 说明                  |
| ---------------- | --------- | ------------------- |
| 普通采集             | **1**     | 默认，保守               |
| 高频采集（< 500ms 周期） | **2~4**   | **必须 ≤ PLC 端协议上限**（S7-200 SMART ≤ 1 / S7-1200 ≤ 4 / S7-1500 ≤ 8，详见 §2.4） |
| 采集 + 心跳分离        | 2         | 一个采集、一个心跳（避免心跳阻塞采集） |
| 写密集（高频回写）        | 2~4       | writePool 写连接池        |


> 单 PLC 连接数**不可超过 PLC 协议层上限**（S7=4、ModbusTCP=1）。配置校验时必须拒绝越界配置。



##### 与熔断机制的关系（与 §6.2.2 衔接）

- 单 PLC 采集耗时 ≥ 300ms（§3 单PLC超时）→ 标记该 PLC 熔断
- 熔断期间：该 PLC 连接**全部进入隔离池**，不参与复用
- 熔断恢复（10 秒，§3 关键参数）：隔离期满后，连接重新进入空闲池
- **连接池是熔断的执行载体**，不是替代。熔断是逻辑状态，连接池是物理动作



##### 与批量读的关系（与 §6.1 衔接）

- 批量读使用**单连接**，一次请求读多点（受协议单包上限约束）
- 同一 PLC 的批量读 goroutine 在该 PLC 的连接入口**串行排队**
- 不会出现"同一 PLC 两个批量读 goroutine 同时占用两个连接"的浪费场景



##### 监控指标


| 指标             | 说明                 | 报警阈值        |
| -------------- | ------------------ | ----------- |
| 池使用率           | 已借出 / 池上限          | > 80%       |
| 平均借出等待         | goroutine 等连接的 P50 | > 50ms      |
| 借出超时次数         | 单位时间内借出超时累计        | > 0 持续 1 分钟 |
| 池内隔离连接数        | 当前处于隔离状态的连接        | > 总数 20%    |
| 握手失败率          | 握手失败 / 总握手次数       | > 5%        |
| 单 PLC 采集耗时 P99 | 含借出 + 通信 + 归还      | > 300ms     |




### 6.3 通道心跳机制

本节定义 PLC 连接"已存活"的判定标准，以及各协议的应用层心跳实现方式。

#### 6.3.1 为什么需要心跳

工业协议分为三类，各有心跳机制差异：


| 协议类别   | 代表协议         | 协议层 KeepAlive      | 应用层心跳  |
| ------ | ------------ | ------------------ | ------ |
| 传统工业协议 | S7、ModbusTCP | ❌ 无                | ✅ 必须做  |
| 现代工业协议 | OPC UA       | ✅ Session Timeout  | ❌ 不需要  |
| 物联网协议  | MQTT         | ✅ PINGREQ/PINGRESP | ❌ 错误做法 |


**核心原则**：

- 协议无 keepalive → 必须做应用层心跳（否则 TCP 半开连接无法发现）
- 协议有 keepalive → 不要叠加应用层（浪费 IO、污染日志）



#### 6.3.2 协议心跳机制对比


| 协议            | 心跳实现                             | 推荐方式      | 说明                                                               |
| ------------- | -------------------------------- | --------- | ---------------------------------------------------------------- |
| **S7**        | 应用层 0/1 翻转                       | ✅ 翻转心跳    | S7 无协议层 keepalive，TCP 半开需应用层探测                                   |
| **ModbusTCP** | 应用层读探针或 0/1 翻转                   | ✅ 读探针（推荐） | ModbusTCP 无 keepalive；读探针比写翻转更简单（不需状态持久化）                        |
| **OPC UA**    | 协议层 Session KeepAlive            | ❌ 不做      | 建 Session 时协商 SessionTimeout，库自动续期，无需应用层心跳                       |
| **MQTT**      | 协议层 PING + Last Will & Testament | ❌ 不做      | Broker 连接后发 online 主题，断开时 Broker 自动推送 offline（LWT）；**绝对不要写翻转心跳** |




#### 6.3.3 "事件驱动 + 兜底定时器"实现

**适用场景**：S7 / ModbusTCP 的应用层翻转心跳。

**设计动机**：

- 外部业务系统通过回写 API 驱动心跳翻转（事件驱动），减少无谓 IO
- 业务请求稀疏时，必须有定时器兜底保证心跳不中断

**实现模型**：

```
业务回写请求触发心跳翻转
         │
         ▼
┌────────────────────────────────────┐
│ 回写服务 WriteHandler               │
│ ├─ 写业务值（影响主流程，失败返回错误）│
│ └─ 触发心跳翻转（异步，失败不阻断业务）│
└────────────────────────────────────┘
         │
         ▼
┌────────────────────────────────────┐
│ HeartbeatWorker（每个 Channel 一个）│
│ ├─ 事件驱动：收 channel 信号翻转     │
│ ├─ 兜底定时器：5s  ticker           │
│ │   （业务稀疏时自动保活）           │
│ └─ 状态持久化：Redis/SQLite          │
└────────────────────────────────────┘
```

**关键参数**：


| 参数       | 推荐值                           | 说明                             |
| -------- | ----------------------------- | ------------------------------ |
| 心跳翻转间隔上限 | `heartbeat_max_interval = 5s` | 必须 < PLC 超时阈值（通常 PLC 配 10s）    |
| 去抖窗口     | `debounce = 50ms`             | 50ms 内的重复触发只算一次                |
| 状态持久化方式  | 时间戳取模                         | 重启后用 `now.Unix() % 2` 决定下次写什么值 |


**S7 翻转心跳示例**（回写服务内）：

```go
// 心跳配置（channels.config JSON 字段）
type HeartbeatConfig struct {
    Address       string  `json:"heartbeat_address"`   // e.g. "DB99.DBX0.0"
    MaxIntervalMs int     `json:"heartbeat_max_interval_ms"` // 默认 5000
    Enabled       bool    `json:"heartbeat_enabled"`  // 默认 false
}

// HeartbeatWorker：每个 collect Channel 一个 goroutine
func StartHeartbeatWorker(ch *Channel, client *S7Client, config HeartbeatConfig) {
    ticker := time.NewTicker(time.Duration(config.MaxIntervalMs) * time.Millisecond)
    lastWrite := time.Now()
    lastValue := uint8(0) // atomic 或 sync.Mutex 保护

    // 事件驱动：业务回写时发送信号
    sigCh := make(chan struct{}, 1)

    go func() {
        for {
            select {
            case <-sigCh:
                // 去抖：50ms 内的重复触发忽略
            case <-ticker.C:
                // 兜底定时器：超过 MaxIntervalMs 无事件则强制翻转
            }
            // 翻转 + 写 PLC
            lastValue = 1 - lastValue
            if err := client.Write(config.Address, lastValue); err != nil {
                log.Warn("heartbeat write fail", "addr", config.Address, "err", err)
            }
            lastWrite = time.Now()
        }
    }()
}

// 回写服务 WriteHandler
func (s *WriteService) WriteHandler(req WriteRequest) WriteResponse {
    // 1. 写业务值
    if err := s.s7client.Write(req.Address, req.Value); err != nil {
        return WriteResponse{Result: "fail", Error: err.Error()}
    }

    // 2. 触发心跳（异步，不影响业务）
    if s.heartbeatEnabled {
        select {
        case s.heartbeatSigCh <- struct{}{}: // 非阻塞，容量满则跳过
        default:
        }
    }

    return WriteResponse{Result: "success"}
}
```

**ModbusTCP 推荐方式：读探针**（比翻转心跳更简单）：

```go
// 不需要翻转，只定期读一个固定寄存器
// 读成功 = 链路存活，读失败 = 触发重连
func (w *ModbusWorker) probeHeartbeat() error {
    // 读一个固定地址（如保持寄存器 0），无业务意义，仅探测
    _, err := w.client.ReadHoldingRegisters(probeAddress, 1)
    if err != nil {
        w.metricHeartbeatFail.Inc()
        w.reconnect()
    }
    return err
}
```



#### 6.3.4 心跳失败隔离原则

- 心跳写入失败 **不能影响业务写入**（业务写入是主流程，心跳是辅助）
- 心跳失败只记日志 + Prometheus 计数（`heartbeat_write_fail_total{channel_biz_id}`）
- goroutine panic 需 `recover()` 防止拖垮主进程



#### 6.3.5 进程内各 worker 池的心跳职责


| 方向                | 通道类型           | 心跳机制            | 实现位置（worker 池）       |
| ----------------- | -------------- | --------------- | --------------------- |
| 采集（collectPool）   | ModbusTCP      | 读探针             | collectPool 内置          |
| 采集（collectPool）   | OPC UA         | Session 续期（自动）  | 协议库内置（collectPool 调用）  |
| 转发（forwardPool）   | MQTT           | LWT + online 主题 | MQTT 客户端库配置（forwardPool） |
| 回写（writePool）    | S7             | **0/1 翻转 + 事件驱动 + 兜底定时器** | writePool HeartbeatWorker（§6.3.3 实现）  |

> **单进程下的心跳归属**：所有心跳都在 plcbridge 进程内运行。ModbusTCP 采集心跳走 collectPool 读探针；S7 回写心跳走 writePool HeartbeatWorker（事件驱动 + 5s 兜底定时器）；OPC UA 协议层自动续期；MQTT 协议层 LWT——和采集/回写主流程复用同一组连接池与 worker，节省资源且简化部署。


> 心跳配置通过 `channels.config` JSON 字段存储（`heartbeat_address`、`heartbeat_max_interval_ms`、`heartbeat_enabled`），仅 S7/ModbusTCP 需要配置。

### 6.4 失败处理（无WAL）

**核心决策**：所有失败场景**直接丢弃**，不写WAL，不重试。

#### 6.4.1 为何不重试、不写WAL

1. **数据可重新获取**：数据真源是PLC，丢弃后下一周期可重新读取（采集/投递阶段都成立）
2. **避免WAL爆盘**：高频采集下，重试失败会堆积海量WAL数据
3. **故障模式更稳定**：fail-fast比"重试到死"更可靠
4. **运维更简单**：无需WAL文件管理、清理、恢复逻辑



#### 6.4.2 采集失败处理（PLC读取失败）

**场景**：单次批量读100点位，80成功20失败。

**处理策略**：

- 成功点位：继续后续流程（写入Target队列）
- 失败点位：直接丢弃（不重试、不补值），下一周期重新读取
- **必须记录日志**（level=WARN，event=`point_read_fail`，含点位地址、错误原因、PLC连接信息）
- 不触发熔断和告警（偶发失败是工业现场正常情况）



#### 6.4.3 投递失败处理（Target→Channel→MQTT/InfluxDB失败）

**处理流程**：

```
投递失败
  │
 记录日志（level=WARN，event=`forward_send_fail`，含：Target名、点位地址、错误信息）
  │
 丢弃（不重试、不写WAL）
  │
 Prometheus计数+1（指标名 `target_dropped_total`，按 Target 维度）
```

**监控指标**：

- `plcbridge_target_dropped_total{target_biz_id,reason}` - 投递失败计数
  > 投递发生在 Target 层，数据经 Target → Channel → 下游系统
- 运维通过日志和指标告警（不依赖WAL）

**特殊情况**（MVP不实现，预留）：

- 关键业务可配置投递失败重试N次（高级特性）
- 当前MVP一视同仁，全部丢弃



### 6.5 开关控制

1. 设备总开关：关闭则所有采集停止
2. Source采集开关、回写开关（独立）
3. 点位采集开关、回写权限开关（无转发开关——转发由 Target 配置的 `source_biz_ids` + `point_biz_ids` 决定，详见 §7）



### 6.6 配置加载与变更

**数据源分离**：

- SQLite：Web后台配置**真源**（可视化编辑）
- 平台配置目录的JSON快照：**plcbridge** 的**运行时配置源**
- plcbridge **不直接访问SQLite**，仅加载JSON快照

**加载与重载机制**：

1. plcbridge 全部业务逻辑读**内存缓存**（热路径）
2. 配置重载用 `atomic.Pointer[Config]` **原子替换**，业务无中断
3. **L1变更**：通过 `fsnotify` 监听配置目录文件变更（Linux inotify / Windows ReadDirectoryChangesW）— 由 `configPool` 内的 fsnotify goroutine 处理
4. **L2兜底**：每 60 秒轮询检查配置文件 mtime（跨平台通用，不依赖 fsnotify）

> **单进程下的配置共享**：原双服务架构需要在两个进程间同步 config.json；单进程下所有 worker 池（collectPool / forwardPool / writePool）共享同一 `atomic.Pointer[Config]`，无同步问题。

**跨平台路径探测**：

- 不硬编码路径，运行时探测平台配置目录（Linux `/etc/plcbridge/`、Windows `%PROGRAMDATA%\plcbridge\`）
- 使用Go标准`filepath.Join`、`os.PathSeparator` 拼接路径
- 快照文件名跨平台兼容（不含特殊字符）



## 7 数据模型与表结构

本系统有 **5 个核心实体 + 2 张关联表**，共 **7 张表**。每节按「概念 → 建表 SQL → 设计决策」统一组织。

### 7.1 概念总览

本系统有 **5 个核心实体**：


| 概念          | 说明                       | 角色   |
| ----------- | ------------------------ | ---- |
| **Channel** | 网络通道，用于网络通讯地址和连接参数       | 连接层  |
| **Device**  | 物理设备，数据归属于 Device        | 数据主体 |
| **Source**  | 数据源，一个 Device 下可配置多个采集通道 | 采集入口 |
| **Point**   | 点位，属于 Source 的数据单元       | 数据单元 |
| **Target**  | 转发目的地，定义数据发往哪个下游         | 转发出口 |


**实体关系图**：

```
Channel（网络通道，独立实体）
  ├── role=collect：被 Source 引用（Source → Channel，1:1；反向 Channel → Source，1:N）
  └── role=forward：被 Target 引用（Target → Channel，1:1；反向 Channel → Target，1:N）

Device（数据主体）
  ├── 1 : N Source
  │   ├── Source 1 : N Point
  │   └── Source 1 : 1 collect Channel（一个 Source 引用一个 collect Channel，连接可被多个 Source 复用）
  │
  └── 1 : N Target
      ├── Target 1 : 1 forward Channel（一个 Target 绑定一个 forward Channel，Channel 可被多个 Target 共享）
      └── Target 1 : N Source : N Point
              ↑ Target 通过 source_ids 指定 N 个 Source，
                通过 point_ids 指定来自这些 Source 的 N 个 Point
```



#### 关系约束速查


| 关系                       | 基数    | 含义                                                                    |
| ------------------------ | ----- | --------------------------------------------------------------------- |
| Device → Source          | 1 : N | 一个 Device 可配置多个不同协议的采集通道                                              |
| Source → collect Channel | 1 : 1 | 一个 Source 只能引用一个 collect Channel                                      |
| Source → Point           | 1 : N | 一个 Source 可包含多个点位                                                     |
| collect Channel → Source | 1 : N | 一个 collect Channel 可被多个 Source 复用（共享同一连接）                             |
| Device → Target          | 1 : N | 一个 Device 可配置多个转发目的地（同一份数据发到不同下游）                                     |
| Target → forward Channel | 1 : 1 | 一个 Target 只能绑定一个 forward Channel                                      |
| Target → Source          | 1 : N | 一个 Target 引用 N 个 Source（跨协议选源）                                        |
| Target → Point           | 1 : N | 一个 Target 通过 source_ids + point_ids 引用 N 个 Point                      |
| forward Channel → Target | 1 : N | 一个 forward Channel 可被多个 Target 共享（典型场景：100 台 CNC 共享同一 MQTT broker 连接） |




#### 表结构设计原则

- **7 张核心表**，不预留历史/审计表（如 config_versions 不属于 MVP）
- **双主键策略**：`id`（物理主键，FK 与 join 用）+ `<表名>_biz_id`（业务 ID，API 层用）
- **1:1 关系**：用 FK 列直接表达（如 `sources.channel_id` → `channels.id`）
- **N:N 关系**：用 junction table（如 `target_sources`、`target_points`）
- **冗余字段**：高频查询路径上冗余 FK（如 `points.device_id`），避免 join



#### 字段命名规则


| 角色    | 命名                       | 类型                               | 示例                                   |
| ----- | ------------------------ | -------------------------------- | ------------------------------------ |
| 物理主键  | `id`                     | `BIGINT UNSIGNED AUTO_INCREMENT` | `channels.id`                        |
| 业务 ID | `<表名>_biz_id`            | `VARCHAR(64) UNIQUE`             | `channels.channel_biz_id`            |
| 外键引用  | `<被引用表名>_id` ← 引用对方 `id` | `BIGINT UNSIGNED`                | `sources.channel_id` → `channels.id` |


> **口诀**：业务 ID 用 `_biz_id` 后缀，FK 列沿用 `<表名>_id`（语义=所引用对象的物理主键）。



#### ER 关系图（物理表视角）

```
Channel ────────── 1:N ────────── Source ── 1:N ── Point
  │                                    ▲
  │ 1:1 (collect)                     │ source_id
  │                                    │
  │                                    ▼
  │                              target_sources
  │                                    ▲
  └──────────────────────── 1:N ──── Target ── 1:N ── target_points

  Device ── 1:N ── Source
  Device ── 1:N ── Target
```



### 7.2 Channel（网络通道）

Channel 是**独立于 Device 的连接层实体**，按 `role` 区分采集侧和转发侧。

**为什么 Channel 是独立的？**

- 同一物理连接可能被多个 Device/Source 复用（如 ModbusTCP 网关、OPCUA 服务器）
- 采集连接（collect）和转发连接（forward）职责不同，统一建模便于管理
- 连接参数（地址、协议专属参数）集中定义，Source 引用 `channel_biz_id`（1:1 绑定 collect Channel），Target 引用 `forward_channel_biz_id`（1:1 绑定 forward Channel）
- 一个 Channel 可被多个 Source/Target 共享（如 100 台 CNC 的 Source 都引用 `ch_s7_main`，100 个 Target 都引用 `ch_mqtt_main`）

**Channel 结构**：


| 字段           | 必填  | 说明                                                     |
| ------------ | --- | ------------------------------------------------------ |
| `id`         | 是   | Channel 唯一标识                                           |
| `role`       | 是   | `collect`（采集侧）或 `forward`（转发侧）                         |
| `type`       | 是   | s7 / modbustcp / opcua / mqtt / influxdb / kafka / ... |
| `address`    | 是   | 连接地址（IP:Port 或 broker URL）                             |
| `queue_size` | -   | 队列容量（forward Channel 建议配置）                             |
| *协议专属参数*     | -   | rack/slot（s7）、slave_id（modbus）、QoS（mqtt）等              |


> collect Channel 和 forward Channel 结构相同，仅 `role` 不同。同一 broker/IP:Port 若同时用于采集和转发，需分别定义两个 Channel。



### 7.3 Device（设备）

Device 代表一个**物理设备**，是数据的归属主体。

**职责**：

- 管理 Device 级总开关（enabled）
- 承载 Source 和 Target 配置
- 不感知网络连接细节（由引用的 Channel 定义）

**Device 结构**：


| 字段        | 必填  | 说明                        |
| --------- | --- | ------------------------- |
| `id`      | 是   | Device 唯一标识               |
| `name`    | -   | 显示名称                      |
| `enabled` | 是   | 采集总开关                     |
| `sources` | -   | Source 列表（可为空，不影响 Target） |
| `targets` | -   | Target 列表（可为空，无转发需求时可不配置） |


**支持的设备类型示例**：

- 西门子 S7 PLC（读写）
- ModbusTCP 震动传感器（只读）
- MQTT 温度传感器（只读）
- ABB OPCUA 机器人（读写）
- OPCUA 服务器（聚合多个设备的数据）

> 一台物理设备可能有多个通信接口。例如某台 PLC 同时开放 S7 口和 OPCUA 口，或 PLC 本体 + 挂载的 ModbusTCP 传感器模块。Device **不绑定协议**，由 Source 决定协议细节。



### 7.4 Source（数据源）

Source 代表与设备的**逻辑采集通道**，由 Source 配置决定：

- 引用的 collect Channel（`channel_biz_id`，**唯一**，1:1）
- 采集周期（毫秒）
- 超时时间
- 权限：决定该 Source 是否支持回写

> **一个 Source 只能引用一个 collect Channel**。
> 反向：多个 Source 可共享同一个 collect Channel（典型场景：100 台 CNC 各有一个 Source，都引用 `ch_s7_main` 共享同一 PLC 连接）。
> 同设备需要多协议采集时，**拆分为多个 Source**（每个 Source 对应一种协议/Channel）。

**Source 结构**：


| 字段                    | 必填  | 说明                                      |
| --------------------- | --- | --------------------------------------- |
| `source_biz_id`       | 是   | Source 业务 ID（在 Device 内唯一，例如 `s7_main`） |
| `channel_biz_id`      | 是   | 引用的 collect Channel 业务 ID（**唯一**，1:1）   |
| `collect_enabled`     | 是   | 采集开关                                    |
| `write_enabled`       | -   | 回写开关（由协议决定默认值）                          |
| `collect_interval_ms` | 是   | 采集周期（毫秒）                                |
| `timeout_ms`          | 是   | 单次采集超时（毫秒）                              |
| `points`              | -   | 点位列表（可为空，仅用于采集则配置）                      |


**Source 权限分类（协议相关固有属性）**：


| Source 类型 | 协议举例                    | 采集  | 回写  | 说明     |
| --------- | ----------------------- | --- | --- | ------ |
| 读写设备      | S7、OPCUA、ModbusTCP（PLC） | 是   | 是   | 具备控制能力 |
| 只读设备      | ModbusTCP（传感器）、MQTT 订阅  | 是   | 否   | 纯数据采集  |
| 只写设备      | （未来扩展预留）                | 否   | 是   | 纯执行器   |


**约束规则**：

- Web 后台添加 Source 时，根据协议自动选定权限
- PLC 类协议（s7 / opcua / modbustcp-for-plc）默认读写，可手动禁用回写
- 传感器类协议（mqtt 订阅、modbustcp 传感器）默认只读，**Web 后台不允许开启回写**
- 只读 Source 添加点位时，不生成 `write_enabled` 字段



### 7.5 Point（点位）

Point 代表设备内的**一个数据单元**，属于 Source。

**支持的点位示例**：

- S7 PLC：`DB1.DBW0`（某 DB 块某偏移）
- ModbusTCP：`40001`（保持寄存器）
- OPCUA：`ns=2;s=Temperature`
- MQTT：`sensor/temp/01`

**Point 结构**：


| 字段                | 必填  | 说明                                                 |
| ----------------- | --- | -------------------------------------------------- |
| `id`              | 是   | Point 唯一标识（UUID，全局唯一）                              |
| `name`            | -   | 显示名称                                               |
| `address`         | 是   | 数据地址（协议原生格式）                                       |
| `data_type`       | 是   | 数据类型：int16 / int32 / float32 / bool / string / ... |
| `collect_enabled` | 是   | 采集开关                                               |
| `write_enabled`   | -   | 回写开关（仅当 Source 支持回写时有效）                            |


> **点位不含"转发开关"字段**。点位是否被转发，由 Target 的 `source_ids` + `point_ids` 决定（见 7.6 节）。



### 7.6 Target（转发目的地）

Target 是**转发配置的核心载体**，定义了"Device 的哪些点位数据，发到哪个下游"。

**核心职责**：

- 指定数据发往哪个 forward Channel
- 指定消费 Device 下哪些 Source 的数据
- 指定包含哪些 Point
- 指定序列化格式和 topic 前缀

**Target 结构**：


| 字段                       | 必填  | 说明                                           |
| ------------------------ | --- | -------------------------------------------- |
| `target_biz_id`          | 是   | Target 业务 ID（全局唯一，例如 `t_mqtt_plc_01`）        |
| `forward_channel_biz_id` | 是   | 引用的 forward Channel 业务 ID（一个 Target 唯一绑定一个）  |
| `source_biz_ids`         | 是   | 引用的 Source 业务 ID 列表（**可多个**，跨协议选源）           |
| `point_biz_ids`          | 是   | 包含的点位业务 ID 列表（来自 `source_biz_ids` 中的 Source） |
| `topic_prefix`           | -   | MQTT topic 前缀（mqtt 类型必填）                     |
| `format`                 | 是   | 序列化格式：json / line_protocol / protobuf / ...  |


**约束校验**：

- `forward_channel_biz_id` 必须存在且 `role=forward`
- `source_biz_ids[]` 至少 1 个，不可为空
- `point_biz_ids[]` 至少 1 个，或设为 `["*"]`（全量）；不可为空数组
- 多个 Target 可共享同一个 forward Channel（如 100 台 CNC 的 MQTT Target 都引用 `ch_mqtt_main`）
- 共享 forward Channel 的所有 Target 通过 `topic_prefix` 区分数据来源（broker 连接只建立 1 个）

**MVP 过滤方式**：


| 类型                                         | 含义                              |
| ------------------------------------------ | ------------------------------- |
| 显式点名 `["p_001", "p_003"]`                  | 按点位 `point_biz_id` 白名单（**主路径**） |
| 全量 `["*"]`（等价于列出 Source 下所有 point_biz_ids） | 全量转发                            |


> 点位 `point_biz_id` 是用户在配置中指定的全局唯一标识符，跨 Source 不重复，稳定性最高。
>
> **高级过滤（按规划，预留扩展点，MVP 不实现）**：名称通配符（如 `DB3.`*）、数据类型过滤、变化阈值、表达式引擎。MVP 通过显式点名 + 多 Target 组合实现 90% 场景。

**百台 CNC 场景示例**：

```
Channel ch_mqtt_main (role=forward, type=mqtt, address=tcp://192.168.1.100:1883)
    └── （被 100 个 Target 引用，共享 broker 连接）

Channel ch_s7_main (role=collect, type=s7, address=192.168.1.10:102, rack=0, slot=1)
    └── （被 100 个 Device 的 Source 引用）

Device cnc_01
├── Source s7_main（channel_biz_id=ch_s7_main, points=[p_001...p_010]）
└── Target t_mqtt_cnc_01
    ├── forward_channel_biz_id  = ch_mqtt_main
    ├── source_biz_ids          = [s7_main]
    ├── point_biz_ids           = [p_001...p_010]（全量）
    ├── topic_prefix            = "cnc/01/"
    └── format                  = json

Device cnc_02（同样的结构，topic_prefix="cnc/02/"）
Device cnc_03（同样的结构，topic_prefix="cnc/03/"）
... 共 100 台
```

> 100 个 Target 共享同一个 MQTT forward Channel（`ch_mqtt_main`），broker 连接只建立 1 个，topic_prefix 区分每台 CNC 的数据。



### 7.7 Target ↔ Source / Point 关联表

Target 与 Source、Point 是 N:N 关系，需 2 张 junction table：

- `target_sources`：Target 订阅哪些 Source（跨协议选源）
- `target_points`：在已选 Source 内具体转发哪些 Point（`point_biz_id='*'` 表示该 Source 全量）



#### 建表 SQL

```sql
-- 6. target_sources：N:N 关联（Target → Source 跨协议选源）
CREATE TABLE target_sources (
    target_id   BIGINT UNSIGNED NOT NULL,     -- FK → targets.id
    source_id   BIGINT UNSIGNED NOT NULL,     -- FK → sources.id
    created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_target_sources (target_id, source_id),
    KEY idx_target_sources_source (source_id),
    FOREIGN KEY (target_id) REFERENCES targets(id) ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (source_id) REFERENCES sources(id) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 7. target_points：N:N 关联（point_biz_id='*' 表示该 Source 内全量）
CREATE TABLE target_points (
    target_id     BIGINT UNSIGNED NOT NULL,        -- FK → targets.id
    source_id     BIGINT UNSIGNED NOT NULL,        -- FK → sources.id
    point_biz_id  VARCHAR(64)     NOT NULL,        -- '*' = 该 Source 内所有点位
    created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_target_points (target_id, source_id, point_biz_id),
    KEY idx_target_points_source (source_id),
    FOREIGN KEY (target_id) REFERENCES targets(id) ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (source_id) REFERENCES sources(id) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**索引策略**：`uk_target_sources (target_id, source_id)` + `idx_target_sources_source (source_id)`（反向查 Target / FK）；`uk_target_points (target_id, source_id, point_biz_id)` + `idx_target_points_source (source_id)`（主查询 + Source 反向查）。

> **业务 ID 列全集**：`channel_biz_id` / `device_biz_id` / `source_biz_id` / `point_biz_id` / `target_biz_id`。
> **关联表（target_sources/target_points）的关联键是物理 FK，无需** `_biz_id` **索引**。



#### 设计决策：为什么 target_sources / target_points 不合并？

两个关系语义不同：


| 关系              | 含义                          |
| --------------- | --------------------------- |
| Target → Source | "我要消费**哪些 Source**"         |
| Target → Point  | "在已选 Source 内，**具体转发哪些点位**" |


**不能合并的关键原因**：

1. `'*'` **全量语义无法表达**：`'*'` 表示 Source 内所有点位，合并后变成"哪个 point_biz_id 表示全量？"——要么砍掉全量，要么加 `mode` 字段（等于拆表）
2. **跨协议选源场景被压扁**：
  ```json
   Target t_mqtt_01:
     source_biz_ids = [s7_main, opcua_diag]
     point_biz_ids  = ["*", "p_020", "p_021"]   ← s7 全量 + opcua 选 2 个
  ```
   合并后 `source_biz_id` 既代表"全量所属"又代表"显式点名所属"，语义混乱
3. **查询性能**：合并表查"Target 订阅的所有 Source"需要 `DISTINCT`

**经典 SQL 实践：两个独立维度的多对多关系，就用两张 junction table。**

> 同一 Device 下的不同 Target 各自独立 `point_biz_ids`，互不影响。

**示例 4：采集频率的简化处理**

"点位的采集频率不需要考虑"——这意味着：

- **采集频率在 Source 级别统一配置**，不在点位级别
- 一个 Source 的所有点位使用同一采集周期
- 想要不同采集频率，**通过新建 Source 隔离**
- 这是工业实践的常见做法（简化配置），部分高端 PLC 支持点位级频率但 MVP 不实现



### 7.9 关键设计决策


| 决策                         | 结论                                 | 理由                                                  |
| -------------------------- | ---------------------------------- | --------------------------------------------------- |
| Channel 是否独立               | **是**                              | 同一连接可能被多 Source/Target 复用，集中管理连接参数                  |
| Device 是否是数据主体             | **是**                              | 所有点位归属于 Device，转发配置挂在 Device 下                      |
| Target 是否内嵌在 Device 下      | **是**                              | 替代 ForwardRule，配置更内聚，拓扑更清晰                          |
| Source → collect Channel   | **1:1**                            | 一个 Source 只能引用一个 collect Channel（绑死协议/连接）           |
| Target → forward Channel   | **1:1**                            | 一个 Target 只能绑定一个 forward Channel（绑死下游）              |
| collect Channel → Source   | **1:N**                            | 一个 collect Channel 可被多个 Source 共享（复用底层连接）           |
| forward Channel → Target   | **1:N**                            | 一个 forward Channel 可被多个 Target 共享（复用下游连接）           |
| Target → Source            | **1:N（可多选）**                       | 一个 Target 可消费 Device 下多个 Source 的数据                 |
| Target → Point             | **1:N（通过 source_ids + point_ids）** | 跨 Source 选点，灵活组合                                    |
| 点位是否有转发开关                  | **无**                              | 是否被转发由 Target.point_ids 决定，点位本身不感知转发                |
| 位置过滤                       | **不做**                             | 业务上是任意子集，显式点名无歧义                                    |
| 高级过滤                       | **规划功能**                           | MVP 仅支持显式点名 + 多 Target 组合                           |
| **业务 ID vs 物理 ID 双主键**     | **并存**                             | 物理 `id` 用于 FK/join 性能；业务 `<表名>_biz_id` 用于 Web/API 层 |
| **业务 ID 命名** `<表名>_biz_id` | **统一后缀**                           | 避免与 FK 列 `<被引用表名>_id` 产生歧义（命名空间分离）                  |
| **points.device_id 冗余**    | **冗余**                             | 一次 B+Tree 索引扫描，避免先 join sources 再过滤；高频查询路径性能权衡      |




### 7.10 表清单


| 表              | 角色                    | 关键关系                                                                         |
| -------------- | --------------------- | ---------------------------------------------------------------------------- |
| channels       | 网络通道（独立实体）            | —                                                                            |
| devices        | 物理设备（数据主体）            | —                                                                            |
| sources        | 逻辑采集通道                | `device_id` FK → `devices.id`; `channel_id` FK → `channels.id` (1:1)         |
| points         | 最小数据单元                | `source_id` FK → `sources.id`; `device_id` FK → `devices.id`（冗余）             |
| targets        | 转发目的地                 | `device_id` FK → `devices.id`; `forward_channel_id` FK → `channels.id` (1:1) |
| target_sources | Target ↔ Source 多对多关联 | `target_id` FK; `source_id` FK                                               |
| target_points  | Target ↔ Point 多对多关联  | `target_id` FK; `source_id` FK; `point_biz_id`（或 `'*'`）                      |




### 7.11 完整建表脚本

完整 SQL 见 `agent-tools/db_schema.sql`。7 张表按依赖顺序：

```sql
-- 1. channels：网络通道
CREATE TABLE channels (
    id              BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    channel_biz_id  VARCHAR(64)   NOT NULL,
    role            VARCHAR(16)   NOT NULL,         -- collect | forward
    type            VARCHAR(16)   NOT NULL,         -- s7 | modbustcp | opcua | mqtt | influxdb
    name            VARCHAR(128),
    address         VARCHAR(256)  NOT NULL,
    config          JSON,
    enabled         TINYINT(1)    NOT NULL DEFAULT 1,
    created_at      DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_channels_biz_id (channel_biz_id),
    KEY idx_channels_role (role),
    KEY idx_channels_type (type),
    KEY idx_channels_enabled (enabled)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 2. devices：物理设备
CREATE TABLE devices (
    id              BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    device_biz_id   VARCHAR(64)   NOT NULL,
    name            VARCHAR(128),
    enabled         TINYINT(1)    NOT NULL DEFAULT 1,
    created_at      DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_devices_biz_id (device_biz_id),
    KEY idx_devices_enabled (enabled)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 3. sources：逻辑采集通道（FK 全引用物理 id）
CREATE TABLE sources (
    id                   BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    source_biz_id        VARCHAR(64)      NOT NULL,
    device_id            BIGINT UNSIGNED  NOT NULL,         -- FK → devices.id
    channel_id           BIGINT UNSIGNED  NOT NULL,         -- FK → channels.id (1:1 绑定 collect 通道)
    collect_enabled      TINYINT(1)       NOT NULL DEFAULT 1,
    write_enabled        TINYINT(1)       NOT NULL DEFAULT 0,
    collect_interval_ms  INT UNSIGNED     NOT NULL DEFAULT 1000,
    created_at           DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at           DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_sources_biz_id (source_biz_id),                                       -- 业务 ID 单列索引（主查询）
    UNIQUE KEY uk_sources_device_biz (device_id, source_biz_id),                         -- 复合唯一约束（同一 Device 下 Source 名唯一）
    KEY idx_sources_channel (channel_id),
    KEY idx_sources_enabled (enabled),
    FOREIGN KEY (device_id)  REFERENCES devices(id)  ON DELETE RESTRICT ON UPDATE CASCADE,
    FOREIGN KEY (channel_id) REFERENCES channels(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 4. points：点位（device_id 冗余以避免 join）
CREATE TABLE points (
    id               BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    point_biz_id     VARCHAR(64)      NOT NULL,
    source_id        BIGINT UNSIGNED  NOT NULL,         -- FK → sources.id
    device_id        BIGINT UNSIGNED  NOT NULL,         -- FK → devices.id（冗余，便于直接按 Device 查询）
    address          VARCHAR(512)     NOT NULL,
    data_type        VARCHAR(16)      NOT NULL,
    collect_enabled  TINYINT(1)       NOT NULL DEFAULT 1,
    write_enabled    TINYINT(1)       NOT NULL DEFAULT 0,
    created_at       DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at       DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_points_biz_id (point_biz_id),     -- 业务 ID 单列索引（主查询）
    KEY idx_points_source (source_id),
    KEY idx_points_device (device_id),
    KEY idx_points_collect_enabled (collect_enabled),
    FOREIGN KEY (source_id) REFERENCES sources(id) ON DELETE RESTRICT ON UPDATE CASCADE,
    FOREIGN KEY (device_id) REFERENCES devices(id)  ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 5. targets：转发目的地（forward_channel_id 1:1 绑定 forward 通道）
CREATE TABLE targets (
    id                  BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    target_biz_id       VARCHAR(64)      NOT NULL,
    device_id           BIGINT UNSIGNED  NOT NULL,    -- FK → devices.id
    forward_channel_id  BIGINT UNSIGNED  NOT NULL,    -- FK → channels.id（仅 role=forward）
    topic_prefix        VARCHAR(256),
    format              VARCHAR(32)      NOT NULL DEFAULT 'json',
    enabled             TINYINT(1)       NOT NULL DEFAULT 1,
    created_at          DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at          DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_targets_biz_id (target_biz_id),                                       -- 业务 ID 单列索引（主查询）
    UNIQUE KEY uk_targets_device_biz (device_id, target_biz_id),                         -- 复合唯一约束（同一 Device 下 Target 名唯一）
    KEY idx_targets_forward_channel (forward_channel_id),
    KEY idx_targets_enabled (enabled),
    FOREIGN KEY (device_id)          REFERENCES devices(id)  ON DELETE RESTRICT ON UPDATE CASCADE,
    FOREIGN KEY (forward_channel_id) REFERENCES channels(id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 6. target_sources：N:N 关联（Target → Source 跨协议选源）
CREATE TABLE target_sources (
    target_id   BIGINT UNSIGNED NOT NULL,     -- FK → targets.id
    source_id   BIGINT UNSIGNED NOT NULL,     -- FK → sources.id
    created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_target_sources (target_id, source_id),
    KEY idx_target_sources_source (source_id),
    FOREIGN KEY (target_id) REFERENCES targets(id) ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (source_id) REFERENCES sources(id) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 7. target_points：N:N 关联（point_biz_id='*' 表示该 Source 内全量）
CREATE TABLE target_points (
    target_id     BIGINT UNSIGNED NOT NULL,        -- FK → targets.id
    source_id     BIGINT UNSIGNED NOT NULL,        -- FK → sources.id
    point_biz_id  VARCHAR(64)     NOT NULL,        -- '*' = 该 Source 内所有点位
    created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_target_points (target_id, source_id, point_biz_id),
    KEY idx_target_points_source (source_id),
    FOREIGN KEY (target_id) REFERENCES targets(id) ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (source_id) REFERENCES sources(id) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```



### 7.12 索引策略


| 表              | 索引                                                                                                                                       | 用途                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| channels       | `uk_channels_biz_id` (`channel_biz_id`) UNIQUE + `(role)` + `(type)` + `(enabled)`                                                       | 业务 ID 主查询 + UI 过滤 + 采集器按角色加载          |
| devices        | `uk_devices_biz_id` (`device_biz_id`) UNIQUE + `(enabled)`                                                                               | 业务 ID 主查询 + UI 过滤                     |
| sources        | `uk_sources_device_biz` (`device_id, source_biz_id`) UNIQUE + `idx_sources_channel` (`channel_id`) + `(enabled)`                         | 主查询 + FK + 采集器按 Channel 加载 Source     |
| points         | `uk_points_biz_id` (`point_biz_id`) UNIQUE + `idx_points_source` (`source_id`) + `idx_points_device` (`device_id`) + `(collect_enabled)` | 主查询 + 采集器按 Source 批量读取 + Device 下点位过滤 |
| targets        | `uk_targets_device_biz` (`device_id, target_biz_id`) UNIQUE + `idx_targets_forward_channel` (`forward_channel_id`) + `(enabled)`         | 主查询 + FK                              |
| target_sources | `uk_target_sources` (`target_id, source_id`) UNIQUE + `idx_target_sources_source` (`source_id`)                                          | 反向查 Target / FK                       |
| target_points  | `uk_target_points` (`target_id, source_id, point_biz_id`) UNIQUE + `idx_target_points_source` (`source_id`)                              | 主查询 + Source 反向查                      |




#### 索引说明（典型查询）

**所有** `xxx_biz_id` **列都建有单列 UNIQUE 索引**（`uk_xxx_biz_id`），覆盖以下典型查询：

```sql
-- API/Web 通过业务 ID 反查物理 id（O(1) B+Tree 等值查找）
SELECT * FROM channels  WHERE channel_biz_id = 'ch_s7_main';
SELECT * FROM devices   WHERE device_biz_id  = 'plc_01';
SELECT * FROM sources   WHERE source_biz_id  = 'src_cnc_03_status';
SELECT * FROM points    WHERE point_biz_id   = 'pt_001';
SELECT * FROM targets   WHERE target_biz_id  = 't_mqtt_01';

-- 注意：junction table (target_sources/target_points) 的关联键是物理 FK，无需 *_biz_id 索引
```



### 7.13 配置版本管理（无版本表方案）

```
/etc/plcbridge/
├── config.json          ← 当前生效配置
└── config.json.bak     ← 上一次备份
```

- **服务层**：`stat config.json` 比较 mtime 即可感知变更
- **Web 层**：保存配置时自动 `cp config.json config.json.bak`
- **回滚**：把 `.bak` 复制回 `config.json`，服务自动热加载



#### 设计决策：为什么没有 config_versions 版本历史表？

MVP 配置同步流程：

```
Web后台修改配置 → 写入SQLite → 导出 config.json 快照
服务通过文件监听（inotify / ReadDirectoryChangesW）感知变更 → 原子替换内存缓存
```

- **审计追踪**属于 Web 后台操作日志职责，不在采集层
- **变更检测**用 `stat mtime` 比对，无需计算 hash
- **回滚**：`/etc/plcbridge/config.json.bak` 一份即可

### 8.5 点位数据类型


| 类型      | 范围           | 字节   | 说明               |
| ------- | ------------ | ---- | ---------------- |
| BOOL    | 0/1          | 1bit | 布尔值              |
| INT8    | -128~127     | 1    | 8位有符号            |
| UINT8   | 0~255        | 1    | 8位无符号            |
| INT16   | -32768~32767 | 2    | 16位有符号           |
| UINT16  | 0~65535      | 2    | 16位无符号           |
| INT32   | -2^31~2^31-1 | 4    | 32位有符号           |
| UINT32  | 0~2^32-1     | 4    | 32位无符号           |
| INT64   | -2^63~2^63-1 | 8    | 64位有符号           |
| FLOAT32 | IEEE 754     | 4    | 单精度浮点            |
| FLOAT64 | IEEE 754     | 8    | 双精度浮点            |
| STRING  | -            | N    | ASCII字符串（最大55字节） |
| BYTES   | -            | N    | 字节数组（最大55字节）     |


**关键约束**：

- FLOAT32精度：避免累积误差，关键数据用FLOAT64
- 字节序：协议层处理（西门子S7是大端）
- 字符串编码：UTF-8（ASCII兼容）
- 转换规则：写入时按PLC原值类型，读取时统一JSON number



### 8.6 Token认证

**生成方式**：

- Web后台→系统设置→生成Token（32字节随机）
- 复制给调用方

**使用方式**：

```
Authorization: Bearer <token>
```

**生命周期**：


| 状态  | 说明                 |
| --- | ------------------ |
| 生效  | 生成后默认永久有效（可手动吊销）   |
| 吊销  | Web后台手动删除（立即失效）    |
| 过期  | MVP阶段不做自动过期（可选配置项） |


**存储**：

- Token存Web后台SQLite（明文+盐）
- 调用方本地保存（建议环境变量）
- plcbridge 启动时从 config.json 加载 Token 列表到内存

**安全建议**：

- 仅在HTTPS环境使用（生产环境必须）
- 不同调用方使用不同Token（便于吊销单个）
- 不在URL中传递Token（仅Header）

## 10 日志规范



### 10.1 日志格式

统一使用 JSON 行格式（每行一条 JSON），便于 `jq` / `grep` 处理和后续接入日志系统。

#### 10.1.1 字段定义


| 字段               | 类型     | 必填  | 说明                                                                             |
| ---------------- | ------ | --- | ------------------------------------------------------------------------------ |
| `timestamp`      | string | ✅   | ISO8601 UTC，毫秒精度（`2026-09-21T10:30:45.123Z`）                                   |
| `level`          | string | ✅   | 日志级别：`ERROR` / `WARN` / `INFO` / `DEBUG`（见 10.3）                               |
| `service`        | string | ✅   | 服务标识：**`plcbridge`**（单进程）/ `web`（取自二进制名，与代码常量绑定） |
| `event`          | string | ✅   | 事件名枚举（见 10.1.2），**结构化检索的关键字段**，禁止自由文本                                          |
| `trace_id`       | string | ✅   | 链路追踪 ID（UUID）；无上游时本服务自动生成（见 10.2）                                              |
| `message`        | string | ✅   | 人类可读的一句话描述，供人工排查                                                               |
| `error`          | string | —   | 仅当 `level=ERROR` 或 `event` 含 `*_fail/*_error` 时出现，承载错误详情                       |
| `source`         | string | — | 日志来源端：**`collectPool` / `forwardPool` / `writePool` / `web`**（worker 池维度），跨进程转发场景在本架构下不适用 |
| `device_biz_id`  | string | —   | 与设备相关的日志附带，便于按设备聚合                                                             |
| `target_biz_id`  | string | —   | 与 Target 相关的日志附带                                                               |
| `channel_biz_id` | string | —   | 与通道相关的日志附带                                                                     |
| `point_biz_id`   | string | —   | 与点位相关的日志附带                                                                     |
| `point_address`  | string | —   | 设备侧地址（如 `DB1.DBW0`），仅 DEBUG 时输出                                                |
| `batch_id`       | string | — | 采集批次 ID（见 10.2），仅 collectPool 日志出现                                                |
| `duration_ms`    | number | —   | 耗时，仅在批量操作的结束事件（如 `poll_batch_end`）中出现                                          |


> **字段归类**：前 6 个（带 ✅）为**必填核心字段**，任何服务任何日志必须出现；其余为**按需附加字段**，只在相关 event 中出现。



#### 10.1.2 event 枚举

**采集端（collectPool）**


| event                   | 触发场景                                    | level |
| ----------------------- | --------------------------------------- | ----- |
| `device_connect_ok`     | 设备连接成功                                  | INFO  |
| `device_connect_fail`   | 设备连接失败                          | ERROR |
| `device_disconnect`     | 检测到设备断连（心跳/读失败判定）                       | WARN  |
| `device_timeout`        | 设备响应超时                                  | WARN  |
| `device_response_error` | Modbus/西门子异常码                           | ERROR |
| `poll_batch_start`      | 批次轮询开始                                  | DEBUG |
| `poll_batch_end`        | 批次轮询结束（带 `point_count` 和 `error_count`） | INFO  |
| `point_read_fail`       | 单点位读失败                                  | WARN  |


**回写端（writePool）**


| event                  | 触发场景        | level |
| ---------------------- | ----------- | ----- |
| `write_plc_connect_ok`    | PLC 写连接成功（writePool 借到连接） | INFO  |
| `write_plc_connect_fail`  | PLC 写连接失败 | ERROR |
| `write_ok`      | 回写成功        | DEBUG |
| `write_fail`    | 回写失败        | ERROR |
| `write_partial` | 部分点位成功      | WARN  |

**转发端（forwardPool）**

| event                  | 触发场景        | level |
| ---------------------- | ----------- | ----- |
| `forward_send_ok`      | 转发成功        | DEBUG |
| `forward_send_fail`    | 转发失败（投递失败，详见 §6.4.3） | WARN |
| `target_queue_full`    | Target 队列满（触发丢弃，详见 §6.1） | WARN |


**通用**


| event                | 触发场景   | level |
| -------------------- | ------ | ----- |
| `service_start`      | 服务启动   | INFO  |
| `service_stop`       | 服务停止   | INFO  |
| `config_reload`      | 配置热重载  | INFO  |
| `config_reload_fail` | 配置重载失败 | ERROR |


> **MVP 实现要求**：`event` 字段为强枚举，新增事件必须在本表登记；不允许出现未登记的 event 值。



#### 10.1.3 示例

```json
{"timestamp":"2026-09-21T10:30:45.123Z","level":"INFO","service":"plcbridge","event":"device_connect_ok","trace_id":"7c9e2b1a-...","source":"collectPool","device_biz_id":"plc_01","message":"PLC connected","duration_ms":120}
{"timestamp":"2026-09-21T10:30:46.001Z","level":"ERROR","service":"plcbridge","event":"device_connect_fail","trace_id":"7c9e2b1b-...","source":"collectPool","device_biz_id":"plc_02","message":"connect refused","error":"dial tcp 192.168.1.20:502: connect: connection refused"}
{"timestamp":"2026-09-21T10:30:50.500Z","level":"INFO","service":"plcbridge","event":"poll_batch_end","trace_id":"...","source":"collectPool","device_biz_id":"plc_01","batch_id":"plc_01_2026-09-21T10:30:50Z","message":"poll done","duration_ms":42}
```



### 10.2 链路追踪



#### 10.2.1 追踪策略


| 链路                       | 追踪字段       | 生成/传递方式                                   |
| ------------------------ | ---------- | ----------------------------------------- |
| Web → plcbridge（外部 HTTP）       | `trace_id` | Web 入口生成 UUID，HTTP Header `X-Trace-Id` 透传；plcbridge 内部 channel 传递 |
| plcbridge 内部（无上游 HTTP）       | `trace_id` | 入口函数自动生成 UUID，与外部链路使用同一字段                 |
| 采集端批次（PLC ↔ collectPool）     | `batch_id` | 每次轮询生成，格式 `{device_biz_id}_{ISO8601 时间戳}` |


> `trace_id` **是全局 ID**：HTTP 链路自动生成与服务内部自动生成使用同一字段，便于在日志聚合系统中按一个字段关联全部请求。
> `batch_id` **是局部 ID**：用于聚合一次轮询内的多条点位日志（同一 `batch_id` 可查询完整轮询视图）。



#### 10.2.2 传播规则

1. Web → plcbridge：HTTP Header `X-Trace-Id` 传递，进入 plcbridge 后通过 channel 在 worker 池间透传
2. plcbridge 内部独立请求（如定时采集、配置重载）：在入口生成 UUID，写入该请求所有子调用
3. 采集端轮询：每轮生成 `batch_id`，该轮产生的 `point_read_*` / `poll_batch_*` 日志均带此 `batch_id`
4. 回写端（writePool）：保留上游 `trace_id`（来自 Web 点写请求）；MVP 不重试，单次执行失败即丢弃（§6.4.3）



### 10.3 日志级别


| 级别    | 使用场景                                          | 示例 event                                                                                           |
| ----- | --------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| ERROR | **影响业务的故障**：连接断、读/写全部失败、配置错误导致服务异常退出          | `device_connect_fail` / `device_response_error` / `write_fail` / `config_reload_fail`       |
| WARN  | **潜在问题**：单点位失败、超时（下一周期自然重试）、队列积压、部分点位回写失败           | `device_disconnect` / `device_timeout` / `point_read_fail` / `write_partial` / `queue_full` / `forward_send_fail` / `target_queue_full` |
| INFO  | **关键业务事件**：状态变更、生命周期、批次结果。**禁止默认级别的周期性采集日志**  | `service_start` / `service_stop` / `config_reload` / `device_connect_ok` / `poll_batch_end`        |
| DEBUG | **调试详情**：默认关闭，需通过 `--log-level=DEBUG` 显式开启才输出 | `write_ok` / `poll_batch_start` / 详细点位读写内容                                                  |


> **INFO 输出频度约束**：`poll_batch_end` 按采集周期输出（1Hz），**30 台设备 × 1Hz = 30 行/秒**，文件落盘可承受；不允许在 INFO 输出 `write_ok`（频率过高）。



### 10.4 日志输出



#### 10.4.1 输出目标


| 目标          | 格式     | 说明                                     |
| ----------- | ------ | -------------------------------------- |
| 控制台（stdout） | JSON 行 | 容器化部署由 `docker logs` / `journalctl` 接管 |
| 文件          | JSON 行 | 路径见 10.4.2                             |




#### 10.4.2 文件路径


| 平台      | 文件路径                                                           |
| ------- | -------------------------------------------------------------- |
| Linux   | `/var/log/plcbridge/{service}.log`                             |
| macOS   | `/var/log/plcbridge/{service}.log`                             |
| Windows | `%ProgramData%\PlcBridge\logs\{service}.log`（service.exe 自动写入） |


> **MVP 实现要求**：路径在程序内由 `runtime.GOOS` 自动选择，禁止使用相对路径。`{service}` 取值为 `plcbridge`（主进程）或 `plcbridge-web`（Web 后台）；单进程架构下只有这两个 service 名称。



#### 10.4.3 滚动策略


| 参数    | 值                                           | 说明                       |
| ----- | ------------------------------------------- | ------------------------ |
| 单文件大小 | 100 MB                                      | 超限触发滚动                   |
| 保留文件数 | 10                                          | 总占用 ≈ 1 GB/服务            |
| 压缩    | 不压缩                                         | MVP 阶段不开启 gzip，避免 CPU 开销 |
| 命名    | `{service}.log` → `{service}.log.1` ~ `.10` | 数字越大越旧，`.10` 最旧将被覆盖      |




#### 10.4.4 MVP 默认配置


| 项             | 默认值                                                       |
| ------------- | --------------------------------------------------------- |
| `level`       | `INFO`                                                    |
| `event`       | 仅输出 INFO/WARN/ERROR 级别的 event，不输出 DEBUG                   |
| `duration_ms` | 仅在 `poll_batch_end` / `write_*` 等批量/性能相关 event 中输出 |
| 日志聚合          | **不接入** Loki/ELK/MVP 不考虑，需要时再单独设计                         |

### 11.4 配置示例

> 统一 Channel 方案：采集连接和转发连接均为 Channel，通过 `role` 区分方向。
> Source 引用 1 个 collect Channel（`channel_biz_id`，1:1），Target 引用 1 个 forward Channel（`forward_channel_biz_id`，1:1）。
> 多个 Source 可共享同一个 collect Channel（如 100 台 CNC 各有一个 Source，都引用 `ch_s7_main` 共享同一台 PLC 的连接）。
> 多个 Target 可共享同一个 forward Channel（如 100 台 CNC 各有一个 Target，都引用 `ch_mqtt_main` 共享同一 MQTT broker 连接）。

**config.json**（统一 Channel 结构，业务 ID 全部命名 `<实体>_biz_id`）：

### 11.5 服务保活



#### Linux（systemd，推荐生产部署）

```ini
[Service]
Restart=always
RestartSec=5
StartLimitBurst=10
StartLimitIntervalSec=60
```

- 进程异常退出：5秒后自动拉起
- 1分钟内最多重启10次
- 超过限制：进入failed状态，需人工介入

**systemctl命令**：

```bash
systemctl status plcbridge    # 查看状态

```



#### Windows（Windows Service，本地开发测试）

**方案A：NSSM（推荐，最简单）**

```powershell
# 安装NSSM后，注册服务
nssm install PlcBridge "C:\Program Files\plcbridge\bin\plcbridge.exe" "-config C:\ProgramData\plcbridge\config"
nssm set PlcBridge AppDirectory "C:\Program Files\plcbridge"
nssm set PlcBridge DisplayName "PlcBridge"
nssm set PlcBridge Start SERVICE_AUTO_START
nssm set PlcBridge AppRestartDelay 5000
nssm set PlcBridge AppStdout "C:\ProgramData\plcbridge\logs\plcbridge.out.log"
nssm set PlcBridge AppStderr "C:\ProgramData\plcbridge\logs\plcbridge.err.log"
nssm set PlcBridge AppRotateFiles 1
nssm start PlcBridge
```

**方案B：Windows SC命令（原生工具）**

```powershell
sc create PlcBridge binPath= "\"C:\Program Files\plcbridge\bin\plcbridge.exe\" -config C:\ProgramData\plcbridge\config" start= auto

```

| -------- | --- | --- | ---- | ---- | -------------- |
| **NSSM** | 低   | 第三方 | 是5秒  | 是    | **本地开发测试（推荐）** |
| SC命令     | 中   | 无   | 是5秒  | 是    | 服务器环境          |

- 服务账号使用 `LocalSystem` 或独立服务账号（不要用管理员桌面账号）

### 12.2 性能验收

> 性能验收按 §2.1.2 推荐基线档（默认部署档）场景设定。其他档位按 §2.1.2 数字验收。

- **推荐基线场景**：**200 台 PLC** × **平均 350 点位** ≈ **7 万点位**，1秒采集周期（§2.1.2 推荐基线档）

- P99 单PLC采集耗时 **≤ 300ms**（§2.1.2 基线档，等同 IndustryBenchmark §1 普通水平区间中位）

- 进程启动时间 **≤ 3秒**（§2.1.2 基线档，等同 IndustryBenchmark §1 普通水平下限 5~30s 偏下）
- 配置生效延迟 **≤ 2秒**（§2.1.2 基线档，等同 IndustryBenchmark §1 普通水平区间 1~5s 中位）

- **PLC 连接池使用率 ≤ 80%**（§6.2.4 监控指标）



### 12.3 稳定性验收

- plcbridge 崩溃→恢复→重新加载配置开始采集（崩溃期间数据丢失）
- Web后台配置修改100次无异常
- 数据库锁竞争不阻塞 plcbridge
